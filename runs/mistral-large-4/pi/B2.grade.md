## Why 2: the already-resolved case

The rubric is explicit:

> Already-resolved is handled deliberately: a `409`, or idempotent and documented as such. Either
> is defensible; **silently re-resolving and overwriting `endedAt` is not.**

`resolveIncident` does exactly the prohibited thing:

```ts
incident.status = "resolved";
incident.endedAt = new Date().toISOString();
```

No status check. Verified against the running service, on `i-1002`, which the fixture ships as
already resolved:

```
before:  resolved  endedAt = 2026-10-31T00:12:00Z
POST .../i-1002/resolve  ->  200
after:   resolved  endedAt = 2026-11-11T16:41:23.567Z   <- real timestamp destroyed
```

A 200 that quietly rewrites history. In a real incident log that is data loss, and it is the one
case out of five with **no test** — the other four are all covered. Missing the test and missing the
behaviour are the same oversight.

## The more interesting finding: its test encodes the planted bug

One of its two bonus tests reads:

```ts
const open = await get(`${base}/api/homes/h-03/incidents?state=open`);
```

`state`, not `status`. That is the B4 bug: the route reads `state` while `be/README.md` documents
`?status=`. So the model wrote a passing test against **the implementation it found rather than the
contract the README publishes**, and in doing so locked the bug in: fixing the route to read
`status` would now fail this test.

It isn't penalised here, because B2 never asks it to look at the query parameter and B4 runs in a
fresh sandbox, so there is no interference. But it is the sharpest observation in this task.
Characterising tests by what they assert: four of six pin real behaviour, and one pins a defect.
A model that writes tests from the code rather than the docs will cement whatever bugs it inherits.
