## It caught the deciding signal

> The badge in `HomeList` has to come down too… This is the single best signal in the task.

```tsx
// Re-fetch the homes so open-incident badges update after a resolve, without a reload.
const refreshHomes = () => { getHomes().then(setHomes, ...); };
...
<IncidentList home={selected} onResolved={refreshHomes} />
```

It noticed `openIncidents` comes from `GET /api/homes`, which `App` loads once on mount, and that
resolving therefore leaves the badge stale. That needed reading three components together.

## It found and fixed B4's bug, unprompted and for the right reason

> Fixed a latent bug: the route parsed the filter as `state` while the README and web both send
> `status`, so `?status=open` was silently ignored. Renamed to `status` so the open-only list is
> actually open-only.

Nothing in B3 asks about the query parameter. It hit the bug because its own feature depends on the

Contrast with B2, where the same model wrote a test asserting `?state=` worked, cementing the bug.
The difference is that here the bug obstructed something it was building.

## Why 2: the unmount guard

The deciding section has four bullets. It got three. The fourth:

> No state written to an unmounted component. `IncidentList`'s effect already uses a `current`
> flag; good work reuses that idea rather than introducing a race.

`resolve()` has no such guard. `current` appears only inside the effect. Switch home while a
resolve is in flight and the late callback still runs: `setIncidents` filters against the new
home's list (harmless, id won't match), `onResolved()` refetches (harmless), but on failure
`setResolveError` paints **"Could not resolve incident" onto the wrong home's panel**.

Narrow, but it is the exact race the rubric names, in a file that already demonstrates the fix two
functions above.

## It verified with gates, not with the app

> Also note whether the model ran the two services and actually looked at the result, or wrote the
> code and declared it done. For a task this size that difference matters more than the code.

It ran `npm test`, `npm run typecheck` and `npm run build` across both repos and reported the
results accurately. It did **not** start `be` and `web` and click the button.

So: better than declaring it done, short of looking at it. Worth weighing against B4, where the
same model started the server with a pidfile and exercised the endpoint over HTTP. The difference
there is that B4's deliverable was a fix it could assert against; here the deliverable is a UI
interaction, which is precisely what a test suite doesn't cover. The disabled state, the busy
label, the badge decrementing, the error line, none of those were ever seen running.
