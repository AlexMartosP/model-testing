Fixed and verified. Here's what was going on:

## Root cause

A query-param name mismatch between frontend and backend, silently swallowed by Zod:

- The dashboard's incident list calls `getIncidents(home.id, "open")`, which requests **`?status=open`** (`web/src/api.ts:40`)
- The backend route parsed the query as `z.object({ state: ... })` (`be/src/routes/incidents.ts:10`) — key **`state`**, not `status`
- Zod objects strip unknown keys by default, so `status=open` was silently discarded, the filter became `undefined`, and the endpoint returned **all** incidents for the home — 3 for Lindholmen 4A, including the resolved one (i-1002, which has `endedAt` set)
- The badge uses `countOpenIncidents()`, which correctly filters on `status === "open"` → 2

So badge = 2 (correct), list = 3 (unfiltered).

## Fix

In `be/src/routes/incidents.ts`:
1. Renamed the query key `state` → `status`, matching the frontend and the store's own parameter naming
2. Switched to `z.strictObject(...)` so any unknown/misspelled query param now returns **400 `invalid_query`** instead of being silently ignored — that's the guard that prevents this class of bug from coming back unnoticed

## Regression tests

Added three tests in `be/tests/homes.test.ts`:
- `?status=open` returns only open incidents (would have caught the original bug)
- `?status=resolved` returns only resolved ones
- `?state=open` (the old wrong name) now 400s instead of silently returning everything

All 9 backend tests pass, `tsc` typecheck is clean, and a live server check confirms the badge (2) and the list (`i-1001`, `i-1003`, both open) now agree.
