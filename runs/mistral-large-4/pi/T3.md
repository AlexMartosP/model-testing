Yes, that's correct. An index is essentially a sorted data structure (often a B-tree) maintained alongside the table, so every `INSERT`, `UPDATE`, or `DELETE` that touches the indexed column has to also update the index. That's extra disk I/O and CPU work on each write.

A few nuances worth knowing:

- **Updates that don't change the indexed column** don't require an index update — only writes that modify the indexed value (or add/remove rows) do.
- **The cost depends on the index type and count.** More indexes = more write overhead. Composite indexes cover multiple columns with one structure, which can be more efficient than several single-column indexes.
- **Some indexes are nearly free to maintain** (e.g., append-only structures like a BRIN index in Postgres, or LSM-tree based storage where writes go to an in-memory buffer), but the general trade-off still holds.
- **Clustered vs. non-clustered** (SQL Server terminology): a clustered index *is* the table's physical sort order, so it doesn't add a separate structure to maintain — but it still constrains write ordering.

So the rule of thumb stands: index the columns you filter/sort/join on frequently, but don't index everything, since each index taxes your write throughput.
